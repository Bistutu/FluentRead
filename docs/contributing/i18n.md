# 界面国际化维护

FluentRead 支持简体中文、英语、日语、韩语、法语、俄语和西班牙语。界面文案位于 `src/core/i18n/messages/`。

## 架构与资源归属

语言标识、默认值和选择器名称由 `src/core/i18n/language.ts` 维护；纯翻译与资源注册由 `src/core/i18n/index.ts` 维护。`bundles.ts` 只用于构建、用户脚本和测试，扩展运行时通过 `src/platform/i18n/uiLanguageBundles.ts` 按需取得所选语言，不能从页面或后台直接导入完整七语目录。

Vue 语言状态、配置同步及失败回滚位于 `src/ui/i18n.ts`。主动切换必须先取得资源，失败时保留原语言并允许原地重试；旧请求、旧失败和已卸载页面不能覆盖新选择。扩展页面的标题和 `html[lang]` 只写入授权根所属的 document；资源未就绪时，`lang` 对应实际显示的中文回退文案。

Vue 组件应使用共享 `useUiI18n()`，不要另建语言 ref 后直接调用纯 `translate()`。按需语言包到达时，语言值可能没有再次变化，组件还需要订阅共享的资源修订信号；否则后台缓存的界面可能一直停留在中文回退结果。

`src/ui/i18n/legacyDom.ts` 独立承载尚未 key 化文案的扫描和观察器生命周期。它是兼容层；新界面和修改较大的设置应直接使用稳定 key。设置补充文案继续按语言维护在 `settings-copy/`，新的独立业务域可以使用自己的小型资源模块，分别接入七语目录。不要让多个资源片段定义相同 key，也不要用修改 legacy 正则的方式处理新的交互状态。

安装功能描述统一位于 `messages/product-descriptions.json`，与 `brand-taglines.json` 的品牌口号分别维护。构建器据此生成浏览器原生 `_locales` 的名称和描述，用户脚本也读取同一份七语描述；商店已有中英资料通过 `pnpm verify:brand` 检查同步。浏览器显示的安装语言由浏览器决定，应用内界面语言由 FluentRead 配置决定。

用户脚本的五语远程包和 Greasy Fork 公共数据使用固定发布基线。构建期由 `userscript/languageBundles.ts` 自动比较当前词典，按脚本实际能力裁剪后生成 gzip 增量；运行时合并新增及修订文案，并依据位置还原模板顺序。修改文案无需另写一份覆盖表，也不要直接改固定 JSON、资源摘要或提交号。GM 缓存只保存原始远程包，增量解压或资源加载失败后可以重试；发布新远程基线仍需遵守原有资源发布流程。

品牌宣传语使用 `brand.tagline`，七语文案统一维护在 `src/core/i18n/messages/brand-taglines.json`。展示位置与静态宣传资料同步方式见 [品牌文案](../../marketing/brand.md)。

## 新增文案

优先使用稳定资源 key，通过 `useUiI18n().t(key, params)` 渲染。七种语言都需要显式提供译文；不要用展开英语词典的方式掩盖遗漏。参数使用命名占位符，不要拼接半句话，以便不同语言调整语序。

提示词帮助中需要原样显示 `{origin}`、`{to}` 等变量名称时，也应显式传入字面值，例如 `t(key, {origin: '{origin}'})`。这样资源缺参检查能区分有意展示变量与遗漏运行参数。

数量文案可提供 `key.plural.one`、`key.plural.few`、`key.plural.many`、`key.plural.other` 等可选变体。调用仍使用基础 key，例如 `t('common.itemCount', {count: 1})`；`count` 为有限数值时按当前语言的 `Intl.PluralRules` 选择词形，再尝试 `other` 和基础文案。不要在组件里写 `count === 1`，俄语等语言的词形规则不止单复数两种。首批数量词形集中在 `count-forms.json`；格式化后的字符串数量仍使用基础文案，避免从字符串猜测数量。

## 设置文案的语境

设置名称应简短，说明先写操作及结果，再补充生效条件。中文短说明一般不加句末句号，相关条件用逗号或分号连接；不要把多个独立意思硬塞进长句，必要时把限制或例外放在单独的提示中。确认对话框、风险说明和示例正文仍可使用完整句子及句号，不对所有文本统一替换标点。

例如，插件开关说明为“关闭后会暂停翻译和写作助手，并隐藏网页及视频中的功能入口；重新开启时恢复原有偏好”。逐句高亮说明放在开关名称下方，先介绍双语模式和鼠标操作，再用完整句子说明句子划分不同时会一起高亮相邻句子。

每种语言按自己的语法和标点书写：日语保留自然的句読点；英语、韩语、法语、俄语和西班牙语的完整句子可保留句号，法语问号、冒号等符号前保留相应空格，西班牙语问句保留起始问号。中文优先用“备用音色”“初次重试等待”等用户能理解的词语；API Key、JSON、CSS、接口地址及占位符保持准确。

设置补充文案集中在 `src/core/i18n/messages/settings-copy/`，每种语言独立维护 `messages`，随对应资源包按需加载。其中的 `legacy` 只为仍在使用的旧源文案或迁移校验保留精确别名。已有旧模板改写时同步更新对应 legacy 词典及人工校正表，避免改完中文后其他语言漏翻；不要在渲染时批量改写句号或扫描用户内容。

尚未迁移到 key 的界面由 `translateLegacyText` 和 UI 指令处理。精确文案存放在对应语言的 legacy 词典；后台与运行时反馈（翻译失败、HTTP 错误、下载和导入进度等）按行表集中在 `runtime-feedback.ts`，机器翻译词条的人工更正放在 `legacy-corrections.ts`，两者在各语言词典末尾展开并覆盖同名旧词条。动态整句模板是纯数据：通用界面模板在 `legacy-patterns.ts`，运行时反馈模板在 `runtime-feedback-patterns.ts`。

模板随非中文语言包一起生成，只在该语言首次使用时编译，非法正则会被跳过。查找顺序为：精确文案 → 前置模板（运行时反馈和本地化整句）→ 按 “ · ”、“ → ” 拆分复合文案 → 后置模板（本语言模板，再回退英语）。模板默认原样保留捕获参数，只允许通过 `localizedCaptures` 标明的界面片段继续本地化；捕获值整体命中词典时优先使用，否则按 “；” 拆分后以目标语言的分隔符重新连接。新增模板前先确认没有被更早的模板遮蔽，`tests/i18n.test.ts` 会用样例值逐条校验模板输出。用户自定义名称、网页原文和模型回答不能作为界面文案翻译。

## 语言恢复入口

通用设置的“软件语言”在非英语界面中保留固定的 `Language` 识别词，帮助初次选错语言的用户找到恢复入口。英语界面不重复显示该识别词。固定英文不依赖英语资源包加载；该标签通过 `data-i18n-ignore` 保护，当前语言部分仍由 `t` 更新。

软件语言选择器在所有界面语言下都保留多语言名称。英语界面使用英文名称与语言自身名称，例如 `Chinese / 中文`、`Japanese / 日本語` 和 `French / Français`；英语选项使用 `English / 英语`。显示规则统一维护在 `src/core/i18n/language.ts`，选中后的名称与下拉选项保持一致。

## 用户内容边界

包含原文、译文、历史问题或单词的节点使用 `data-i18n-ignore`。如果该节点内仍有界面提示，应直接调用 `t` 或 `translateLegacy`，包括 `title`、`aria-label`、`placeholder` 和 `alt`。原生 DOM 控件需要在语言配置变化后主动刷新。

下拉选项若通过 teleport 移到控件之外，父控件的保护不会随之转移。含用户名称的选项需要自己的保护节点；支持输入新选项的控件，还需要将整个菜单挂到受保护的自有容器，覆盖组件内部生成的候选项。

`contenteditable` 用户正文同样不参与旧文案扫描，包括嵌在编辑区中的 `contenteditable="false"` 提及等片段；独立于编辑区的只读控件仍可本地化。项目、网页、章节和自定义服务名称保留原文；“项目：{name}”之类的界面前缀使用完整 key 与命名参数。PDF 页码、DOCX 页眉等产品生成标签依据解析结构本地化，不能仅凭一段文字看起来像页码，就改写用户的同名章节。

Shadow DOM 中安装 i18n 插件后，尚未迁移到资源 key 的组件仍需在自有界面根节点启用 `v-ui-i18n`。写作助手在卡片根节点启用该指令，覆盖风格、语言、状态及辅助标签；服务与模型名称、Markdown 正文和输入值保持原样。语言搜索同时匹配原始名称与当前界面显示的名称。回复语言与阅读对照语言是两个独立偏好，对照正文与模型回答一样使用 `data-i18n-ignore`，不随界面文案扫描改写。可使用 `scripts/testing/run-writing-assistant-test.cjs --suite i18n`，配合隔离浏览器参数验证七种语言、生成状态、内容边界与窄屏布局。

## 检查

运行 `pnpm verify:i18n` 执行语言目录、源码 key、加载失败与并发、设置说明、安装描述和用户内容边界的针对性检查，同时验证文档 CLI 的隔离资源夹具、Popup 入口与设置控件的实际事件契约。测试替身若直接返回稳定 key，应据此寻找控件；不要依赖已迁移的中文标签或旧模块文件位置。`i18n-key-audit.mjs` 使用 TypeScript/Vue 语法树展开可枚举的条件 key，检查资源存在及静态参数对象；真正动态的 key、动态参数和所有交互状态仍需组件测试覆盖。既有中文来源扫描负责迁移层覆盖，两类检查不能互相替代。

运行 `pnpm exec vitest run tests/i18n.test.ts tests/imageTranslationFlow.test.ts`。界面扫描使用语法树检查 Vue 静态文案和展示注册表，检查实际译文及动态模板参数。Vue 编译器会把相邻文本与 `{{ }}` 插值合成一个文本节点，扫描同样按占位值拼接整段文案，并展开插值中的字面量条件分支，避免只检查碎片而漏掉整句。它不能替代动态状态和真实布局检查。

运行 `pnpm compile`、`pnpm test:audit`，按本次改动选择架构与严格覆盖检查，再构建 Chrome、Firefox 和用户脚本。使用隔离浏览器切换全部语言，检查相关设置、弹窗、文档工具以及带数据的状态；语言自身名称、品牌和用户内容应保持原样。普通改动不以全量产品回归替代有边界的 i18n 验证。
